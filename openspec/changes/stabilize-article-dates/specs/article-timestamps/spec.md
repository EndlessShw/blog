# Spec Delta

## Purpose

为博客文章提供含义独立且可跨环境复现的发布时间与更新时间，使读者能够区分首次发布和后续修订。时间应由明确保存的发布元数据及文章、关联本地附件的版本历史决定，避免检出、换行转换和重复部署造成时间漂移。

## ADDED Requirements

### Requirement: 保留既有发布时间

系统 SHALL 将有效的文章 `date` 作为固定发布时间。文章内容、附件、构建时间或操作系统文件时间变化 MUST NOT 自动覆盖已有 `date`。

#### Scenario: 修改已发布文章
- **WHEN** 已有有效 `date` 的文章或其附件发生变更并提交
- **THEN** 发布时间保持原值，更新时间独立计算

#### Scenario: 无效或矛盾的发布时间
- **WHEN** `date` 无法解析，或晚于可推导的更新时间
- **THEN** 系统报告文章路径及具体问题，不擅自改写 `date` 或伪造更新时间以掩盖矛盾

### Requirement: 补齐缺失发布时间

系统 SHALL 提供预览和显式写入操作，仅为缺失 `date` 的文章补写追溯重命名后的首次入库提交时间。操作 MUST 保留正文、已有字段及文件换行格式，重复执行 MUST 不再产生额外变更；首次入库时间 MUST NOT 被宣称为已证实的真实首发时间。

#### Scenario: 缺少日期且有重命名历史
- **WHEN** 文章没有 `date`，且历史中曾移动或重命名
- **THEN** 预览列出文章路径、候选发布时间和来源提交，并追溯到重命名前首次加入的提交；预览不修改文件

#### Scenario: 确认写入后重复执行
- **WHEN** 执行日期补齐写入后再次运行同一操作
- **THEN** 仅首次操作添加缺失日期，后续操作不更改已补齐的日期、正文或其他字段

### Requirement: 本次旧文日期迁移范围受限

系统 SHALL 将本次日期写入范围限制为根仓库 Git 跟踪的 `source/_posts/` 下 Markdown，仅补缺失 `date`。其他目录、被 Git 忽略的工程说明及子模块说明文件 MUST NOT 被写入日期；日期迁移 MUST NOT 顺带改变文章或附件的渲染规则。

#### Scenario: 工程说明也位于文章目录内
- **WHEN** 本地 Hexo 将 `source/_posts/` 内被忽略的 HELP.md 或子模块 README.md 识别为文章
- **THEN** 本次日期迁移仍将其单列，不写日期、不改变其渲染行为

#### Scenario: 文章目录外也有 Markdown
- **WHEN** 仓库其他目录存在 Markdown 或日期字段
- **THEN** 本次迁移不修改这些文件

### Requirement: 更新时间来自有效变更提交

系统 SHALL 从当前版本文章及关联本地附件的有效内容变更历史派生 `updated`，使用相应 Git 提交的提交者时间，取相关有效变更中最近的时刻。编辑、push 和部署时刻 MUST NOT 替代提交时间；已有静态 `updated` MUST NOT 阻止自动更新。

#### Scenario: 编辑提交与推送发生在不同时刻
- **WHEN** 周一编辑文章、周五提交该变更、周六推送并部署
- **THEN** 更新时间对应周五有效内容变更提交的提交者时间

#### Scenario: 无后续修订的新文章
- **WHEN** 文章只有首次入库这一有效内容变更且无更晚附件变更
- **THEN** 更新时间采用首次入库提交时间，而不是构建时刻

#### Scenario: 文件中已有更新时间
- **WHEN** front matter 已有 `updated`，此后文章或其关联附件又发生有效内容变更并提交
- **THEN** 生成页面采用新的历史派生更新时间，不被旧字段固定

### Requirement: 区分内容修改和非内容变更

系统 SHALL 将正文、已有非空标题、标签和排版变化视为更新；仅补齐缺失或空 title、CRLF/LF 转换、内容不变的移动或重命名 MUST NOT 构成更新。除换行符差异外，系统 MUST NOT 一概忽略文本空白；二进制附件按实际内容判断。

#### Scenario: 改错字或标签
- **WHEN** 文章正文、标题或标签发生修改并提交
- **THEN** 更新时间采用该有效修改提交时间

#### Scenario: Markdown 排版变化
- **WHEN** 只修改缩进、段落空行或行尾用于换行的空格并提交
- **THEN** 该排版修改属于有效内容变更

#### Scenario: 纯换行符转换
- **WHEN** 文本仅在 CRLF 与 LF 之间转换，其余内容相同
- **THEN** 保留前一次有效内容变更的更新时间

#### Scenario: 纯移动或重命名
- **WHEN** 文章或关联附件仅改变路径，内容不变
- **THEN** 延续重命名前的内容历史，不以路径变化提交刷新更新时间

#### Scenario: 二进制附件修改
- **WHEN** 被关联的图片或二进制代码附件内容发生变化并提交
- **THEN** 该提交作为有效附件变更参与更新时间计算

#### Scenario: 仅补齐缺失或空标题
- **WHEN** 已有文章仅从没有 title 或空 title 变为填写 title，正文及其他非时间元数据、附件均未变化
- **THEN** 保留前一次有效内容更新时间，不将补标题提交算作内容更新

#### Scenario: 修改已存在标题
- **WHEN** 已有非空 title 被修改，包含将“标题 TODO”替换为正式标题
- **THEN** 该提交构成有效文章更新

### Requirement: 时间字段维护不构成内容更新

系统 SHALL 在判定文章有效内容变更时排除仅维护顶层 `date`、`updated` 的差异，且 MUST 保留对其余元数据和正文变更的识别。

#### Scenario: 仅补齐发布时间
- **WHEN** 提交只为文章增加 `date`，没有其他内容或关联附件变化
- **THEN** 更新时间仍采用补日期前最近的有效内容变更提交

#### Scenario: 同次提交修改时间与正文
- **WHEN** 同一提交同时维护时间字段并修改正文或标签
- **THEN** 正文或标签修改使该提交仍构成有效更新

### Requirement: 自动识别正文的本地附件

系统 SHALL 识别文章实际引用的本地图片和代码文件，包括 Markdown 图片、文件链接及 HTML 资源属性，并按文章和站点资源路径解析。外部 URL、纯锚点、代码示例中的链接文字 MUST NOT 被当成本地依赖；系统 MUST NOT 自动递归分析代码依赖或远程资源。

#### Scenario: 只修改被引用图片
- **WHEN** Markdown 或 HTML 正文引用的本地图片更新并提交，而文章文本没有变化
- **THEN** 所属文章的更新时间反映该图片变更提交

#### Scenario: 指向代码附件
- **WHEN** 正文实际链接本地代码文件，该文件修改并提交
- **THEN** 该文件的有效变更参与文章更新时间计算

#### Scenario: 外链与代码示例
- **WHEN** 正文含远程 GitHub 链接、锚点或代码块中的示例 `src` 字符串
- **THEN** 系统不将其误判为需要追踪的本地文件，远程目标变化不改变本地文章更新时间

### Requirement: 显式声明配套文件和目录

系统 SHALL 允许文章明确声明没有正文链接的配套文件或目录。声明目录时，其受版本控制文件的增加、修改和删除均参与更新计算；不允许只枚举当前仍存在的文件。未被引用或明确归属的同级文件 MUST NOT 自动影响文章。

#### Scenario: 声明未链接的配套工程
- **WHEN** 文章声明 `code/mybatis/` 属于其配套附件，其中受版本控制的源码修改并提交
- **THEN** 即使正文没有本地代码链接，文章更新时间也反映该修改

#### Scenario: 配套目录内新增或删除文件
- **WHEN** 显式归属目录内受版本控制文件新增或删除并提交
- **THEN** 该提交参与文章更新时间计算，删除事件不会因文件已不存在而漏算

#### Scenario: 未归属的同级文件变化
- **WHEN** 同级的其他文章、工程或附件发生变更，但没有与当前文章建立引用或归属关系
- **THEN** 当前文章的更新时间保持不变

#### Scenario: 多篇文章共享同一附件
- **WHEN** 多篇文章引用或明确声明同一附件，该附件修改并提交
- **THEN** 所有关联文章的更新时间均计入该修改

#### Scenario: 配套目录包含已跟踪的产物或子模块
- **WHEN** 显式目录中受版本控制的 `.class`、`.jar` 文件变化，或本仓库记录的子模块版本变化
- **THEN** 这些版本变化参与更新时间计算，不擅自按扩展名排除，也不读取子模块未提交修改来生成线上时间

### Requirement: 跨环境及重复构建一致

系统 SHALL 在相同提交、日期元数据和附件声明下产生相同发布时间与更新时间，不依赖检出时刻、主机时区或 Hexo 处理缓存。自动派生 `updated` MUST NOT 反复改写源 Markdown。

#### Scenario: Windows 和 Linux 检出同一版本
- **WHEN** Windows 使用 CRLF、Linux 使用 LF，且文件检出时间不同
- **THEN** 两边生成的文章时间一致，均以北京时间展示

#### Scenario: 附件变化后使用已有缓存
- **WHEN** 文章 Markdown 未变，关联附件有新的有效提交，且构建复用 Hexo 缓存
- **THEN** 生成页面仍包含新的附件更新时间

#### Scenario: 重复部署无新内容提交
- **WHEN** 同一提交重复生成或部署
- **THEN** 时间保持一致，生成过程不产生源文件的 `updated` 修改

### Requirement: 缺失历史与附件异常可诊断

系统 SHALL 在生成日期前确认所需 Git 历史可用。历史缺失且无法取得时 MUST 明确失败，不回退到文件或当前时间。失效引用、越出仓库的路径及未跟踪附件 SHALL 按文章和路径报告，不伪称其已被完整追踪；已有失效引用报告本身不强制阻断全站构建。

#### Scenario: 浅克隆无法补全历史
- **WHEN** 构建历史不足且无法获取完整所需历史
- **THEN** 构建失败并指出历史问题及可执行的修复方向，不生成看似正常的当前时间

#### Scenario: 被引用文件已删除
- **WHEN** 关联文件曾受版本控制，随后删除，文章仍引用它
- **THEN** 其删除提交参与更新时间计算，同时报告失效引用

#### Scenario: 无历史支持的引用
- **WHEN** 引用指向不存在且无可用历史的路径、仓库外文件或未跟踪文件
- **THEN** 检查结果列出文章、引用和原因，不用文件时间补造其变更历史

### Requirement: 本地预览不制造提交时间

系统 SHALL 对已有 Git 历史的文章以已提交版本计算更新时间。未提交正文或附件编辑 MUST NOT 产生新的提交时间；从未入库的新文章 SHALL 明确提示尚无可推导历史。

#### Scenario: 本地修改尚未提交
- **WHEN** 已跟踪文章或附件存在未提交编辑并进行本地预览
- **THEN** 更新时间仍为最近已提交的有效变更时间，不采用本地保存时间

### Requirement: 页面显示与排序遵循独立时间语义

系统 SHALL 使用 `Asia/Shanghai` 展示文章时间；首页显示发布时间，首页与归档按发布时间排序。文章详情 SHALL 沿用主题原生规则：更新时间与发布时间不同时在文章开头显示更新时间提示；两者相同时只显示发布时间。

#### Scenario: 修订旧文章
- **WHEN** 一篇旧文章产生新的有效更新
- **THEN** 文章详情显示固定发布时间和新的更新时间，首页与归档仍按原发布时间排序

#### Scenario: 两个时间相同
- **WHEN** 文章发布时间与更新时间相同
- **THEN** 按主题原生行为隐藏更新时间提示，保留发布时间

### Requirement: 旧日期更新入口保持发布时间稳定

系统 SHALL 使现有日期更新入口停止使用操作系统修改时间新增或覆盖文章 `date`。如保留旧入口，入口 SHALL 转用统一规则或给出清楚的替代命令，不得继续执行旧时间写入逻辑。

#### Scenario: 使用旧更新命令
- **WHEN** 用户通过原 `update.py` 或其批处理入口处理已有发布时间的文章
- **THEN** 文章发布时间不被文件修改时间覆盖，用户得到统一操作结果或替代方式说明
