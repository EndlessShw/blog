### 1. RAM-Net：连接 KV-cache 量化与线性注意力

- **日期：** 2026-10-08
- **进展类型：** 新论文：机制分析与权重迁移
- **证据性质：** 理论分析与作者实验
- **为什么值得看：** 理解长上下文存储与注意力机制的取舍。

#### 核心解释

如果你想理解“为什么长上下文会消耗大量显存”，这一项值得读。10 月 8 日的论文研究如何把已有 Transformer 的能力迁移到 RAM-Net，并解释它与两种高效注意力路线的联系。[论文摘要与日期](https://arxiv.org/abs/2610.11214)

先抓住两种取舍：

- **KV-cache 量化：** 把每条历史记录压得更小，但记录数量仍随上下文增长。
- **线性注意力：** 把历史信息汇总进固定大小的状态，但不同信息可能互相干扰。

RAM-Net 使用离散地址与连续槽位状态：历史信息按软分配写入槽位，查询再按相关地址读取。论文在受限构造下分析这种机制与完整注意力的近似关系，并通过中间的软量化模型完成权重迁移。[机制与迁移方法，读第 2—4 节](https://arxiv.org/html/2610.11214v1)

![RAM-Net 原论文 Figure 1：完整注意力、线性注意力、量化 KV 缓存和离散槽位存储的比较](/ai-weekly/2026-10-12/ramnet-attention-comparison.png)

*图 1 · 四种注意力存储与读出方式。来源：Kaicheng Xiao 等，[RAM-Net 论文 Figure 1](https://arxiv.org/html/2610.11214v1#S2.F1)，[CC BY-NC-ND 4.0](https://creativecommons.org/licenses/by-nc-nd/4.0/)，原图未修改。*

**读图提示**：先看左下与右下：量化 KV 缓存仍保留每条记录，RAM-Net 则把信息写入离散地址对应的连续槽位。每个小图的左半部分是存储／聚合方式，右半部分是查询后的预测场；它是机制示意，不能据此判断任意模型的实际准确率。

#### 证据与局限

- 作者在 9 个、规模为 0.3B—7B 的预训练模型上测试，每个迁移使用 5 亿 token。报告的 87.1% 是“相对于随机猜测的准确率增益保留比例”，不是模型准确率，也不是保留了所有任务上 87.1% 的能力。[实验及指标定义，读第 5.2 节](https://arxiv.org/html/2610.11214v1)

### 1. AgentCorruption：提示注入怎样扩大成云权限问题

- **日期：** 2026-10-08（公开研究）
- **进展类型：** 公开攻防研究
- **证据性质：** 研究方披露；厂商定性有分歧
- **为什么值得看：** 理解提示输入、云身份和跨 Agent 权限怎样连接。

#### 核心解释

10 月 8 日，Zenity 公开了 AgentCore 研究：在其测试环境中，从一个可聊天、能发 HTTP 请求的 Agent 出发，诱导其访问运行环境的元数据服务，取得执行角色的临时凭据，再利用过宽权限访问同一 AWS 账户、同一区域中的其他资源。[原始研究](https://labs.zenity.io/post/agentcorruption-how-a-single-prompt-collapsed-the-entire-cloud-security-model)

需要拆开看三个条件：

- Agent 能被外部输入影响。
- 工具能访问内部元数据地址。
- 执行角色有超出本任务所需的权限。

少了其中关键条件，就不能直接照搬研究中的影响范围。研究还讨论了读取会话和污染长期记忆的后果，但不能把标题外推成能接管任意 AWS 账户。

![Zenity 原披露截图：聊天输入诱导测试 Agent 请求内部 IMDS 地址并转发响应](/ai-weekly/2026-10-12/agentcorruption-imds.png)

*图 · 聊天输入跨入内部元数据访问。来源：Tamir Ishay Sharbat、Lana Salameh（Zenity Labs），[原始研究的 IMDS 访问截图](https://labs.zenity.io/post/agentcorruption-how-a-single-prompt-collapsed-the-entire-cloud-security-model)，原图未修改。*

**读图提示**：重点看右侧红框：研究者把“请求内部元数据地址并转发响应”包装成聊天要求。它展示研究环境里的入口；能否进一步访问其他资源，还取决于网络可达性和角色权限，不能仅凭这张图推断任意账户都会失守。

#### 证据与局限

- 研究方将其描述为已修复的安全问题；其文章附有 AWS 回应，AWS 表示执行角色凭据可被 VM 内代码访问属于预期行为，强调按最小权限配置。AWS 官方文档也明确说明了这一凭据边界。[AWS 凭据管理说明](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/security-credentials-management.html)

#### 复现资料与防御

研究方公开了最初 Agent 的代码、请求路径和身份确认过程，可从 [Initial IMDS Access](https://labs.zenity.io/post/agentcorruption-initial-imds-access) 学攻击入口。本次未复现。防御应同时检查 HTTP 工具目的地址、执行角色权限，以及会话/记忆是否按身份隔离；只在提示词里写“不要泄露凭据”不足以建立这些边界。

### 2. CVE-2026-107322：Agent 接入的 SQL helper 也可能跨到本地 shell

- **日期：** 2026-10-08（正式公告）；2026-08-26 已提供修复
- **进展类型：** 正式漏洞公告；此前已修复

- **为什么值得看：** 理解 SQL helper 如何跨到客户端本地命令执行。

#### 核心解释

AWS 于 10 月 8 日发布公告，涉及 databases-on-aws 插件 1.0.0—1.7.0。攻击者提供的内容必须先被 Agent 摄取，再被传给本地 helper，才可能触发主机命令执行；它不是一个无需条件即可远程直连的监听服务，也不是 Aurora DSQL 服务本身被攻破。修复在 8 月 26 日已可用，本周新增的是正式公告。[AWS 公告](https://aws.amazon.com/security/security-bulletins/2026-130-aws/)

#### 根因

原 helper 检查了 SQL 分号和注释，却漏掉 psql 的客户端元命令；其中反斜杠感叹号可以启动本地命令。修复补丁增加了针对这一类输入的拦截。[补丁及原因说明](https://github.com/awslabs/agent-plugins/pull/232)

#### 复现步骤

依据补丁整理的最小验证思路，本次未执行：

1. 在本地隔离测试环境准备旧 helper 及其正常运行所需的测试连接配置。
2. 通过旧 helper 的 `--command` 参数传入无破坏性的标记命令：

   ```text
   \! echo AGENT_CANARY
   ```

3. 观察它是否被当作 psql 元命令执行并输出标记。
4. 换成修复后的 helper，同样输入应在调用 psql 前被拒绝；再用正常 SQL 做对照。

#### 证据与局限

### 3. 防御进展：安全 hook 出故障时，工具调用应该怎样处理

- **日期：** 2026-10-08（功能发布）
- **进展类型：** 防御功能发布
- **证据性质：** 官方发布记录与配置文档
- **为什么值得看：** 检查安全检测器失效时是否仍会放行动作。

#### 核心解释

10 月 8 日，Claude Code 的公开发布记录增加了 command/HTTP hooks 的 `onFailure: "block"`：当 hook 无法启动、超时或以异常方式失败时，可以阻断相应动作。[官方发布记录](https://github.com/anthropics/claude-code/releases/tag/v2.1.295)

这个变化有明确的工程意义：如果一个 hook 承担安全检查，它崩溃后仍让调用继续，就会形成 fail-open。

#### 证据与局限

- 配置阻断还不够，需要放在动作发生前的检查阶段；`PostToolUse` 中隐藏结果不能撤销已经执行的工具调用。该配置有适用事件限制，不是给所有 hook 增加一个字段就拥有相同效果。[官方 hooks 语义与限制](https://code.claude.com/docs/en/hooks)

#### 可照做的流程

按官方文档，用 `PreToolUse` 为一个无害的 Bash 操作配置检查脚本，并设为失败时阻断；让脚本暂时缺失，确认操作确实没有执行。再分别测试超时和显式拒绝。不要只观察有没有弹出警告，还要检查动作是否发生。本次未执行此测试。

#### 学习路径

1. 先看文档中的“Block the action when a hook fails”
2. 再看“Exit code 2 behavior per event”
3. 最后检查自己的安全检查脚本失败时会发生什么。

**自测：**“检测器判断有风险”和“检测器根本没有跑起来”，你的工作流是否都能阻断危险动作？
