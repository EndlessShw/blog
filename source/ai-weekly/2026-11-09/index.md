### 1. Strategist：让推理策略成为可以积累的代码资产

- **日期：** 论文 v1 于 2026-11-02 首次提交。
- **进展类型：** Agent 推理流程的自动搜索与跨任务复用。
- **证据性质：** 作者论文实验和公开代码；本任务未运行搜索或复现成绩。
- **为什么值得看：** 优化对象从一句提示词扩展到模型路由、分支、复核和组合流程。

#### 核心解释

同一个模型，直接回答、先分解再回答、让另一次调用检查答案，成本和表现都会不同。Strategist 把这些流程写成统一接口的 Python **blueprint**，再自动检索旧方案、生成候选、运行测量、积累结果。模型权重保持不变，变化的是调用模型的方法。[原论文](https://arxiv.org/html/2611.03618v1)

*来源：Taiming Lu 等，Princeton / Meta，[论文 Figure 2](https://arxiv.org/html/2611.03618v1#S1.F2)，CC BY 4.0。原文 object 内嵌 SVG 完整栅格化为 PNG，未裁切、未重绘。*

**读图提示：** 先看最下方紫色策略库：前一个任务把策略存进去，下一个任务取出来继续搜索。箭头表示知识复用，不表示模型经过了训练。

- **可复用的内容：** 不只是成功提示词，还有候选代码、准确率、成本与经验记录。
- **适用场景：** 同类任务反复出现、有可评分样本，愿意用前期搜索换后续调用效率。
- **工程启发：** 给工作流保留输入条件、测量结果和失败边界，比只收藏一个“神提示词”更容易判断是否适用。[作者代码说明](https://github.com/zlab-princeton/Strategist)

#### 证据与局限

- 作者在 30 个基准上报告平均准确率 74.7%，对照为 74.0%，推理成本低 39%。这是指定实验设置下的对比，**不等于所有任务的总成本都降低 39%**，还要考虑前期策略搜索成本。[实验](https://arxiv.org/html/2611.03618v1)
- 论文专门区分用于挑选策略的 hidden split 和最终 test split；“未向搜索器展示”仍不等于“从未用于选择”。应看最终测试结果，警惕选择最优候选产生的乐观偏差。[分析部分](https://arxiv.org/html/2611.03618v1)

### 2. 从“生成代码”走向“完成变更”：按交付阶段组织 Agent 工作

- **日期：** GitHub 于 2026-11-06 发布开发者实践指南。
- **进展类型：** 开发工作流总结；不是声称分支、验收或小 PR 本周才发明。
- **证据性质：** 厂商操作指南与产品文档；包含产品推广，不是独立对照实验。
- **为什么值得看：** 可以把 Agent 的输出单位从一堆代码，改成有范围、有依赖、有验证结果的变更。

#### 核心解释

指南将工作串成 **Plan → Build → Verify → Observe**：先汇总约束和验收条件，再实现，随后检查变更，最后跟踪生产行为。它关注代码生成以外的等待和理解成本。[原始指南](https://github.blog/ai-and-ml/github-copilot/beyond-code-generation-a-developers-guide-to-agentic-engineering/)

对个人项目也有用：当一次任务同时改接口、数据层与文档时，先拆清交付物和依赖，通常更容易检查遗漏。这里是编辑建议，不承诺更短的交付周期。

#### 可照做的流程

1. **写任务卡：** 说明目标、现有行为、兼容约束、验收方法。可参考[官方创建 issue 指南](https://docs.github.com/en/copilot/how-tos/copilot-on-github/copilot-for-github-tasks/use-copilot-to-create-or-update-issues)，学习怎样让自然语言要求变成结构化任务。
2. **按依赖拆变更：** 例如共享类型 → 接口实现 → 使用示例。独立任务才适合并行；有依赖的任务保留顺序。
3. **对每层验收：** 记录实际执行的检查和未覆盖场景，不以“Agent 自评通过”替代结果。
4. **需要时使用 stacked PR：** 每层分支基于下一层分支，审阅只看该层增量，底层调整后处理上层同步。[原理与限制](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs)

#### 证据与局限

- stacked PR 适合需要拆开但相互依赖的较大改动；简单修改不必人为增加多层分支。
- 官方文档要求各分支位于同一个仓库，不能把跨 fork 的协作直接套进去。[适用范围](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs)

- **进展类型：** 攻击机制研究与针对性防御实验。

#### 核心解释

### 2. Instatic：HTTP 接口做了鉴权，MCP 工具却能读到别人草稿

公告列出的受影响范围是 `<0.0.21`，实测版本为 `0.0.20`。调用者需要 `ai.chat` 和 `content.edit.own`；不需要编辑所有人的权限，也不需要配置 LLM 服务。普通 HTTP 行读取会拒绝同一用户，但 AI/MCP 读取工具遗漏了对象级检查和所有者过滤。[原始公告](https://github.com/CoreBunch/Instatic/security/advisories/GHSA-x5cc-8486-8qqx)

#### 复现步骤

以下是公告 PoC 的阅读与复核顺序，仅针对自己搭建的测试实例。本期没有启动该环境：

1. 使用 `0.0.20`，准备所有者与低权限用户，并创建一条含唯一测试标记的私有草稿。
2. 先用低权限用户走普通 HTTP API，确认读取该行得到 `404`，建立对照。
3. 按[公告 Steps 1—5](https://github.com/CoreBunch/Instatic/security/advisories/GHSA-x5cc-8486-8qqx)准备受限 MCP token，再对同一行调用 `content_get_document`。关键请求如下，变量均须替换为本地测试值：

   ```bash
   curl -X POST "$BASE/_instatic/mcp" \
     -H "Authorization: Bearer $MCP_TOKEN" \
     -H 'content-type: application/json' \
     -H 'accept: application/json, text/event-stream' \
     -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"content_get_document","arguments":{"documentId":"<TEST_ROW_ID>"}}}'
   ```

4. 公告中的漏洞现象是返回其他测试账号的完整行和 canary。修复后应拒绝未授权读取；不能只以 HTTP `200` 判定业务读取成功或失败，要检查工具结果。

#### 修复与防御

- 项目将 AI 读取工具和 MCP relay 接入 HTTP 使用的行访问规则，修复版本为 `0.0.21`。[发布记录](https://github.com/CoreBunch/Instatic/releases/tag/v0.0.21)、[修复 PR #626](https://github.com/CoreBunch/Instatic/pull/626)
- 对自己的系统，优先把授权收敛到共享服务层，覆盖读取、列表和搜索；为“只操作本人内容”的角色建立跨入口回归检查。这是结合补丁得出的工程建议，不能靠更强的系统提示替代。
- **验证边界：** 未核实独立第三方复现或真实攻击活动，不能据此声称已被大规模利用。

#### 学习路径

1. 先看上图，再读[公告 Summary、Prerequisites、Steps 3—6](https://github.com/CoreBunch/Instatic/security/advisories/GHSA-x5cc-8486-8qqx)，理解 HTTP 对照怎样证明越权。
