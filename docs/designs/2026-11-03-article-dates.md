# 文章发布时间与更新时间

状态：发布时间补齐已通过 3167153 上线并由用户确认；缺失标题及动态更新时间的补充规则已收敛，尚未实施这两项。后续以 openspec/changes/stabilize-article-dates/ 内的更新设计和规格为准。

## 目标

发布时间固定，文章及其关联本地附件发生内容变化时自动更新更新时间。相同 Git 版本重新检出、跨平台构建或重新部署，所得时间一致。

## 已确认的规则

1. 发布时间与更新时间是两个独立概念，见根目录 GLOSSARY.md。
2. 发布时间优先保留现有 front matter 的 `date`。缺失时，追溯文件重命名，以 Git 历史中首次加入文章的提交时间补齐，之后保持固定。
3. 更新时间采用文章及其附件最近一次有效内容变更的 Git 提交时间，不采用本地编辑时间、push 时间、部署时间或操作系统文件时间。
4. 正文、标题、标签、排版修改均算文章更新。仅 CRLF/LF 转换、文件移动或重命名不算更新。文本中的其他空白不统一忽略，因为 Markdown 空白可能影响排版。
5. 正文引用的本地图片和代码附件自动纳入更新范围。
6. 没有正文链接的配套文件或目录，允许明确指定归属；指定目录时追踪目录内受 Git 管理的文件。不会把所有同级文件自动归给文章。
7. 首页和归档继续按发布时间排序，首页显示发布时间。统一使用 `Asia/Shanghai`；按后续确认沿用 Fluid 原生行为，两个时间不同时在文章开头显示更新时间提示，相同时只显示发布时间。
8. 仅维护 date、updated 时间字段不构成文章内容更新。旧文复核后，用户再次确认已有 date 全保留、缺失用首次入库时间，不恢复历史旧值。本次仅迁移 source/_posts/ 下根仓库跟踪的 124 个 Markdown，额外 9 个工程说明、其他目录与渲染规则不动；见 docs/research/2026-11-03-existing-article-dates.md 及对应补齐预览。

## 已核实的现状

- `_config.yml` 使用 `updated_option: 'mtime'`，未指定时区，首页按 `-date` 排序。
- 当前安装的 Hexo 在缺少 `date` 时回退到文件 birthtime，在缺少 `updated` 且上述配置下回退到 mtime。这些文件时间不能代表文章历史。
- Git 系统配置为 `core.autocrlf=true`，抽样文章为索引 LF、工作区 CRLF，符合正常换行转换规则。
- `update.py` 将 mtime 添加或覆盖到 `date`，并无条件重写文件，没有维护独立的 `updated`。
- Fluid 的文章开头更新时间和底部版权区更新时间均未开启。
- Git 跟踪的 `source/_posts/**/*.md` 共 124 个；该统计未按 Hexo 实际文章识别结果分类。43 个仅含 `date`，35 个有 front matter 但没有日期字段，46 个没有 front matter；没有文件填写 `updated`。
- 本地不是浅克隆，HEAD 可达 81 个提交；最早提交为 2023-12-29。存在多次文章重命名。不能证明这些记录覆盖文章真实首发历史。
- 文章存在大量本地图片引用，包括 Markdown 和 HTML 写法；未找到真实的本地源码文件或代码目录链接。
- 例如 `source/_posts/SSM/mybatis/mybatis.md` 旁边有 `code/mybatis/` 配套工程，但正文没有建立本地代码引用关系，需明确声明归属才能纳入。
- `/code/`、`/range/` 路径中的受版本控制文件包含 `.class`、`.jar` 等。若指定包含它们的目录，这些已跟踪文件也属于更新范围，不能擅自按扩展名排除。
- 仓库未发现 Vercel 部署配置。后续插件核查已证实最近生产部署先恢复缓存，再执行 package.json 的 clean/build，即 hexo clean 与 hexo generate；安装命令是 pnpm install --no-frozen-lockfile。实际克隆深度尚未打印，详见 docs/research/2026-11-03-vercel-github-build.md。

## 建议的实现方式（待随完整方案确认）

### 发布时间迁移

提供可预览、可重复运行的迁移操作：保留现有 `date`，只为缺失日期的实际文章补写时间，不覆盖正文或其他 front matter。先检查所需历史是否可用，再产生变更。

已有 `date` 可能曾被旧脚本写错。本方案不批量重算这些日期，也不把首次入库时间描述为已证实的真实首发时间。无法推导的文章和日期矛盾单独列出，不能用当前时间填补。

### 自动更新时间

在 Hexo 构建阶段计算并设置文章的 `updated`，不把每次生成的更新时间反复写回源 Markdown，避免额外提交和更新循环。

从当前版本的文章及其关联附件追溯有效内容变更，取其中最近的提交时刻。实现采用提交者时间，并沿文件重命名追溯；只改路径且内容不变不构成更新。文本比较只统一 CRLF/LF；二进制附件按其实际内容比较。

显式归属目录内文件的增加、修改、删除均属于目录内容变更，不能只枚举当前仍存在的文件。被引用文件的删除同样是内容变更，并须报告其引用失效。

用户已确认排除仅维护 `date`、`updated` 字段的变更，以免此次补齐日期本身刷新所有文章的更新时间。

每次构建都重新核对附件变化，即使 Markdown 自身没有变化，也不能因为 Hexo 缓存而漏掉附件更新。

### 附件归属

自动识别正文的本地资源引用，按文章及站点的资源路径规则解析；剔除代码示例中的伪链接、外部 URL 和锚点。配套工程支持显式声明文件或目录，声明方式在实现时沿用文章元数据或独立映射中的较简单方式。

不自动递归分析代码的 import、运行时依赖或外部网站内容。指向本地目录时，纳入其受 Git 管理的文件；若目录包含子模块，只能由本仓库记录的子模块版本变更感知其更新，不能检测子模块未提交修改。

已有失效引用、仓库外路径或未跟踪的附件须在预览/检查结果中列出，不得假定其文件时间可靠。对于无法解析的引用，不静默声称已完整覆盖。

### 集成与边界

- 修正旧 `update.py`，使其不能继续用 mtime 覆盖发布时间。
- 保持仓库现有 Hexo、Fluid 和 pnpm 流程，不引入远程服务存储文章时间。
- 在 Vercel 构建路径中保证所需 Git 历史可用；若历史不足且无法获取，明确失败，不回退到部署时间或伪造日期。
- 设置时区，确保文章详情可见发布时间和更新时间。
- 本地未提交编辑不是线上版本，不产生新的 Git 更新时间。预览时保留最近已提交版本的更新时间。
- 只改变当前需求所需文件，保留现有未提交改动。不顺带迁移整个仓库的换行符、清理附件、修改发布排序或修复所有旧链接。

## 验证标准

下列标准随完整方案确认后生效，其中“仅维护时间字段不触发更新”已由用户单独确认。

1. 同一提交重复生成、在不同检出时间生成，发布时间和更新时间一致。
2. 修改正文、标题、标签或排版并提交，发布时间不变，更新时间对应新提交。
3. 只转换 CRLF/LF、纯重命名，或只维护时间字段，不触发内容更新时间。
4. 只修改被引用图片、代码附件或显式归属目录中的文件并提交，也能更新所属文章；无关联文件不会影响文章时间。
5. 缺失 `date` 的文章可补齐，已有 `date` 原样保留；有重命名历史的文章可追溯。
6. 验证实际生成的首页、归档和文章详情：排序及显示符合已确认规则，时区一致。
7. 缺失历史、失效引用等情况可被检查并报告，不能静默采用 mtime。
