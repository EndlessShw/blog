## 结论

Vercel 使用平台提供的 npm/pnpm 等工具安装依赖并执行仓库构建，不等于忽略仓库代码。决定本地修改是否进入部署的是：修改是否提交并推送到关联仓库和分支、项目根目录是否正确，以及实际构建命令是否经过修复入口。

本项目实测已证明：部署 9050e61 克隆了 EndlessShw/blog 的 main，使用 pnpm 安装依赖，然后执行仓库 package.json 的 clean 和 build 脚本。因此，修复逻辑进入这些构建入口并提交推送后，可以沿用现有部署流程；无需因为平台提供包管理器而迁移部署方式。

## 已查证的部署机制

1. Git 集成通常为分支推送生成部署；生产分支用于生产部署，其他分支用于预览。本项目最近生产部署的实际来源已确认是 main；项目的生产分支配置字段本身尚未返回。
2. Install Command 与 Build Command 独立：前者安装依赖，后者生成博客。使用 npm 安装依赖不意味着 Hexo 会忽略本地脚本或配置；这些文件仍须进入所部署的提交。
3. 项目 Root Directory 决定构建根路径。本仓库的 package.json、Hexo 配置和 source 在仓库根目录，但账户内实际 Root Directory 尚未验证。
4. 仓库 vercel.json 的 buildCommand 能覆盖控制台 Build Command。可以显式让 Vercel 调用 package.json 的 build，避免仅修改本地 scripts.build 却没有经过该入口。
5. Vercel 默认浅克隆最近 10 层提交历史。根据 Git 历史计算文章时间之前必须检查历史，按需补齐；不能假定线上与本地历史一样完整。
6. 默认按锁文件检测包管理器；启用 Corepack 时可按 packageManager 指定。不能把“日志里出现 npm”和“线上使用与本地完全相同的依赖及工具版本”视为同一件事。

## 对现有提案的补充建议

- 保持现有 GitHub → Vercel 流程，不因 npm/pnpm 工具差异直接迁移到其他部署方式。
- 将日期修复接入现有统一 build，在 Hexo 生成前检查/准备 Git 历史。日志已经证明当前 build 会被执行，新增 vercel.json 是为了版本化部署配置、防止未来漂移，而不是让本次修复能执行的先决条件。
- 历史补全需在真实环境验证，不承诺仅执行 git fetch --unshallow 就一定成功；还要核对远程地址、访问能力和当前部署提交。
- 当前本地锁文件格式及 packageManager 已不同于这次线上部署。实施时需核对目标包管理器与锁文件兼容性；安装命令带 --no-frozen-lockfile，不能仅因同一提交就承诺依赖解析完全冻结。本次未改云端安装命令，也不顺带升级依赖。
